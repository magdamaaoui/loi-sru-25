## Recording and editing rules

- Record the current website, including the UI improvements already made. Do not recreate the old sidebar layout or orange hover color seen in the meeting.
- Record each major section as a separate take. Leave at least three seconds of still footage before and after important actions. These extra seconds are for editing and are not additions to the five-minute timeline.
- Preserve the visible cause and result of an interaction. Do not cut between a click and the resulting filter change unless the recording fails and a replacement take is needed.
- Cut long travel between sections. Do not include accidental scrolling, overshooting, or cursor searches.
- Keep the section title visible when establishing each component. Keep the active control and the result in the same shot where possible.
- Allow maps and images to load before starting a take. Do not record loading placeholders as part of the demonstration.
- Keep the cursor still during holds. Move it away from text after a click unless it must remain over a tooltip target.
- Hold tooltips without triggering neighboring dots. Do not reproduce the repeated exploratory hovers in the meeting.
- Use the spoken final choices when they differ from exploratory clicks. Skip Netherlands and Germany in the European comparison. Skip Tour Bois-le-Prêtre in the case-study index.
- Do not add the overseas atlas, the health maps, the explanation grid, the housing-health matrix, resident quotes, News Sources, Bibliography, or Lexicon to this cut.
- Do not use the meeting audio as a finished narration track. She explicitly says this is not a voiceover draft.

## Proposed recording workflow

This is a plan only. Do not start the browser rehearsal, capture, or edit until the user asks to proceed.

### 1. Prepare a separate recording setup

Use Playwright to operate a dedicated browser against the deployed URL. Playwright 1.58.2 and FFmpeg are already installed locally. Keep recording scripts separate from the site's application code and existing tests. The existing test configuration starts a local build, so it should not be used unchanged for this production-site recording.

Use a clean browser session with English selected and a fixed 1920 by 1080 viewport. Set the video size explicitly to the same dimensions. Playwright's default video sizing otherwise reduces the output. Capture only the web page, without browser tabs, desktop notifications, or the personal-site wrapper from the meeting.

No Sanity changes, commits, deployments, or production UI changes are needed. Any visible pointer helper would exist only in the recording browser session, would follow the actual scripted mouse position, and would not alter page layout or block input. Validate pointer visibility in the pilot rather than assuming the native cursor will appear in browser footage.

### 2. Rehearse the deployed interactions without recording

Check the planned sections against the current live site. Locate controls and target communes by their names where possible, rather than relying on old screen coordinates. Confirm the map's Paris framing and the introduction's stopping point.

Wait for fonts, images, map tiles, and chart data before each take. Use actual visible readiness checks rather than one fixed loading delay. Keep the site's normal animation enabled.

### 3. Record and approve a short pilot

Capture about 20 to 30 seconds containing a map movement and a scatter tooltip. Check the resulting video for crisp text, a visible pointer, complete map rendering, and smooth motion. Check that the tooltip appears at the intended time and stays readable.

The installed Playwright recorder uses 25 frames per second. Do not promise native 30 or 60 fps, and do not convert to 60 fps and describe that as a smoother capture. If the pilot is satisfactory, use the browser recorder for all takes. If it is not, use the same planned browser actions with a separately validated native screen recorder at a higher frame rate. That fallback may require macOS screen-recording permission. Select and test it before recording the full sequence.

Show the pilot to the user before committing to the appearance and pacing of the complete recording.

### 4. Capture seven independent sections

Capture Introduction, Supply Map, Non-Compliance, European Context, Health scatter, Case index, and Les Jasmins gallery as separate source clips. Record the short navigation moments as needed. The 31 actions in the timeline are editing beats, not 31 separate browser sessions.

Use paced mouse movement, wheel events, and real clicks. Give each visible result time to settle. Log action times so later trims can be matched to the correct interaction. Leave extra still time at both ends of every take. If a take fails, rerecord that section rather than changing its visible result artificially.

### 5. Assemble a silent first cut

Use FFmpeg to trim and join the selected takes in the agreed order. Remove loading and long scrolling between unrelated sections. Preserve the visible sequence from an input to its result. Use simple cuts, with no music or decorative effects by default.

Treat five minutes as a first estimate, not a reason to add empty holds. Keep a timing file separate from the source footage so individual shot lengths can be revised without recording the whole video again.

### 6. Review and finalize

Check the exported file's dimensions, duration, and decoding. Review every interaction and every cut, with denser visual inspection around scrolling and map movement. Give the user the assembled video for full playback review; frame inspection alone cannot certify continuous motion quality.

Confirm the final examples, the selected years, and the ending against this brief. If narration is wanted, approve its wording and record a draft before fixing the final shot lengths. Do not treat the meeting audio as the narration.

Export an H.264 MP4, retaining the source clips and a reproducible edit recipe. Do not commit large video files to the website repository or publish the video without a separate request.
